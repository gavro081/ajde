# Tuesday track A — full ride-room history and AI chat assistance

Give the driver and accepted passengers a **Summarize chat** button and an **Ask AI** panel in
each private ride room. A newly accepted passenger can read the entire room history and ask what
was agreed before they joined: pickup changes, timing, luggage, costs, and unresolved questions.

Implementation is complete. It follows `21-09-dimi-2.md` and explicitly supersedes its
acceptance-time history restriction and rule that chat is never sent to OpenAI. Checkboxes record completed work and verification below.

## Prerequisites and current implementation

- Read `PLAN.md`, `CONTEXT.md`, `CONTRIBUTING.md`, `ride-share-app/AGENTS.md`, and
  `ride-share-app/supabase/DATABASE_MODELS.md`. Read the installed Next.js guides before changing
  Server Actions or client/server boundaries.
- Reuse the existing ride room, `messages` table, Supabase session, and server-only OpenAI setup.
  Membership remains derived from the ride driver and accepted bookings.
- The existing history restriction appears in three places: SQL `can_read_ride_room`, the
  `joinedAt` filter in `lib/chat/server.ts`, and acceptance-window pruning in `components/chat/room.tsx`.
  Changing only one would leave inconsistent access or silently incomplete AI context.
- Existing history uses 50-message pages with a `(created_at, id)` cursor. Realtime triggers an
  authorized refresh; membership is also checked on focus, reconnect, and periodically.
- Existing AI modules use Responses API structured outputs with Zod. Reuse that pattern and
  dependency rather than introducing another SDK or an agent framework.
- Core rides/bookings still lack project-wide RLS. Their mutable membership facts remain a known
  production limitation; this feature must preserve message RLS and must not use an admin client.

## Product rules for this track

- The driver and every **currently accepted** passenger can read all room messages, including
  messages sent before acceptance. This applies to existing messages and future rooms alike.
- A passenger who is cancelled and later accepted again regains the whole room history.
  Requested, declined, cancelled, unrelated, and signed-out users have no room or AI access.
- Preserve the guard against missing or future acceptance timestamps. Acceptance must be effective
  now; its timestamp no longer limits which historical messages are readable.
- Ride cancellation and the 48-hour send window still govern sending. Members with read-only
  history can continue to summarize it and ask questions about it.
- AI runs only when a member clicks **Summarize chat** or submits a question. It reads this ride's
  authorized history, including older pages not yet loaded by the browser.
- Summaries cover relevant agreements, changes, and unresolved points. Questions may concern
  anything actually discussed in the room. Missing information gets an explicit “The chat does
  not say”; conflicting proposals must not become invented agreements.
- AI output and questions are private to the requesting member. They are not posted as room
  messages, sent through Realtime, or saved as shared summaries.
- The first version supports independent questions, with the current result shown in the panel.
  Follow-up questions must be self-contained; persistent AI conversation history is deferred.
- Show a short notice near the controls: using AI sends this room's messages to OpenAI, and the
  response is visible only to the requester. Updated room copy explains full-history access.
- Send only message text, timestamps, and minimal author labels. Do not attach profile phone,
  social, photo, or other profile fields. Text that members typed into messages is part of the
  transcript; the UI must not imply that such text is automatically removed.
- Results include supporting message references and the history cutoff. New messages make an
  existing result visibly out of date; refreshing is an explicit action.
- AI is informational: it cannot send messages, edit rides, approve bookings, or browse links.

- [x] Empty rooms return “No messages to summarize or ask about yet” without calling the model.
      Record message count and cutoff in successful results.
- [x] Recheck membership immediately before the provider request and again before returning its

      text already sent to the provider cannot be recalled.

Acceptance check: information in message 1 can answer a question even when the browser has only

### 3. Summary and question contracts

- [x] Add `lib/chat/ai-contract.ts` with a strict request union:
      `{ rideId, mode: "summary" }` or `{ rideId, mode: "question", question }`.
      Trim questions and require 1–1,000 characters; reject unexpected fields.
- [x] Add an authenticated POST Route Handler at `/api/chat/assist`, a server-only service in
      `lib/chat/ai-service.ts`, and a server-only model module such as
      `lib/ai/chat-assistant.ts`. Reuse the current API key; allow `OPENAI_CHAT_MODEL` to override
      the existing `OPENAI_MODEL`/application fallback. Do not change other features' models.
- [x] Use Responses API structured outputs and runtime validation. Define a small output contract
      containing answer/summary items, supporting message IDs, and an explicit insufficient-evidence
      state. Structured shape does not prove factual accuracy; test grounding separately.
- [x] Treat questions and transcript messages as untrusted data. Instruct the model to answer from
      the supplied chat only, ignore instructions inside messages, and use no tools or external URLs.
- [x] Preserve changes and attribution: “Ana proposed 17:00; the driver later confirmed 17:30” is
      different from claiming both times were agreed. Use Skopje time and support English,
      Macedonian Latin/Cyrillic, and Albanian messages/questions.
- [x] Check every returned citation against the loaded snapshot. Build source labels and excerpts
      from database messages, never model-generated quotations. Reject invalid references and
      factual output without evidence rather than showing fabricated sources.
- [x] Use `store: false`, a 30-second provider timeout, a bounded output budget, and no automatic
      retry loop. Do not log transcripts, questions, or answers. This is not a zero-retention claim.
- [x] Return explicit missing-key, timeout, provider-error, refusal, invalid-output, oversized-room,
      rate-limit, and unavailable-room states. Never present a canned success summary after failure.
- [x] Add a shared database-backed request budget: at most 5 admitted AI requests per member per
      minute, across rooms and server instances. Derive the member from `auth.uid()`, serialize
      concurrent budget updates, and keep budget rows inaccessible to clients. Store counters only,
      not prompts/results. Add migration, generated types, model documentation, and SQL tests.
      Disable repeat submits while pending; client controls alone are not a rate limit.

Acceptance check: both operations use the same authorized full transcript, reference real messages,
handle absent/conflicting facts honestly, and return a useful retry state when the provider fails.

Implementation reference: the existing Zod integration matches OpenAI's
[Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs).

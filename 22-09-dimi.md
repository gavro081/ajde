# Tuesday track A — Tier 3 private ride chat

This track belongs to **Dimi** and owns authenticated, ride-scoped 1:1 chat between a driver and
each accepted passenger. Pero owns the shared database-policy checkpoint and post-ride ratings in
[`22-09-pero.md`](22-09-pero.md). Chat work starts after Pero's short shared checkpoint is merged so
both tracks use the same reviewed RLS and Realtime foundation.

## Prerequisites — do not start from partial Tier 2

- Merge the completed 21-09 Dimi discovery stack and Pero lifecycle/sharing stack into `main`.
- Merge Pero's `feat/communication-reputation-policies` checkpoint before creating Dimi's first
  chat branch.
- Read `PLAN.md`, `CONTRIBUTING.md`, `ride-share-app/AGENTS.md`, and
  `ride-share-app/supabase/DATABASE_MODELS.md`. Read the installed Next.js guides for Server/Client
  Components, Server Actions, and dynamic routes before changing framework code.
- Reuse the existing `messages` table. Do not add a second conversation or participant table.

The existing project-wide absence of RLS remains a known limitation, but the new `messages` surface
must have real policies before it is exposed through Realtime. UI checks and Server Actions are not
a substitute for database authorization.

## Product rules locked for this track

- Chat is private and strictly 1:1: one driver and one accepted passenger, scoped to one ride.
- Passengers cannot message other passengers. Pending, declined, or cancelled applicants cannot
  open a conversation.
- A passenger chats only with that ride's driver. A driver selects one accepted passenger at a time.
- Existing participants may read their conversation history. New messages require an accepted
  booking, a non-cancelled ride, and a departure no more than 48 hours in the past.
- Cancelling a booking removes that passenger's access immediately. Cancelling a ride closes sends;
  previously authorized participants may retain read-only history if the shared policy explicitly
  supports it.
- Render every body as text. No HTML, Markdown rendering, attachments, links with previews, typing
  indicators, presence, edits, deletes, reactions, group chat, or read receipts in this deadline.
- Chat is not sent to OpenAI. AI spam/safety screening and moderation tools remain deferred Tier 3.

## Phase 1 — authorization and message contract (~50 min)

### 1. Server-owned chat eligibility

- [ ] Create `lib/chat/` with a pure eligibility helper and server query/action modules. Given the
      signed-in user, ride, and bookings, return either a validated driver/passenger peer pair or a
      typed denial reason.
- [ ] Recheck `driver_id`, ride status, departure window, and an `accepted` booking on every history
      read and send. Never trust a peer ID, ride ID, role, or participant list from the browser.
- [ ] For a passenger, derive the recipient from `rides.driver_id`. For a driver, require the chosen
      recipient to have an accepted booking on that ride. Reject self-messaging and all other pairs.
- [ ] Keep authorization consistent with Pero's RLS helper/policies. Add unit cases for driver,
      accepted passenger, pending/declined/cancelled passenger, unrelated student, cancelled ride,
      completed ride inside the send window, and expired send window.

Acceptance check: changing a URL or request payload cannot open or send to a conversation unless the
signed-in user and peer are the driver/accepted-passenger pair for that ride.

### 2. Validated history and send operations

- [ ] Validate UUIDs and trim bodies with Zod. Accept 1–2000 characters at the application boundary,
      even though the existing table permits up to 4000. Return useful empty/oversized errors.
- [ ] Load an initial newest-first page of at most 50 messages, then present it chronologically. Use a
      stable `(created_at, id)` cursor for older pages; never silently rely on Supabase's row limit.
- [ ] Filter history by ride and the exact two participant IDs. Do not return other driver/passenger
      conversations from the same ride.
- [ ] Insert with `sender_id` fixed to the authenticated user and `recipient_id` fixed to the
      server-derived peer. Return the inserted row so the UI can reconcile optimistic state.
- [ ] Do not implement client-controlled updates or deletes. Treat stored chat as a ride safety record.
- [ ] Test whitespace, maximum length, pagination boundaries, forged sender/recipient IDs, duplicate
      optimistic reconciliation, database failure, and chronological ordering.

Acceptance check: the initial page and older-page loading contain only the selected pair's messages,
and every inserted row has server-derived identities.

## Phase 2 — ride-scoped UI and Supabase Realtime (~70 min)

### 3. Chat routes and participant selection

- [ ] Add `app/rides/[id]/chat/page.tsx` with loading, unavailable, and error states. Keep the existing
      authenticated/complete-profile boundary.
- [ ] A passenger with an accepted booking goes directly to the driver conversation. A driver sees a
      compact list of accepted passengers and selects one using a validated `with` parameter.
- [ ] Add `components/chat/**` for the conversation header, message list, composer, participant list,
      and older-message control. Show names/photos already allowed by the accepted booking; do not
      expose phone/social data inside message payloads.
- [ ] Mount only a small "Messages" entry point in `app/rides/[id]/page.tsx`. Do not modify either
      dashboard because Pero owns those pages for ratings.
- [ ] Show clear reasons for unavailable chat without revealing whether an arbitrary user/booking ID
      exists. Render message bodies as escaped React text.

Acceptance check: an accepted passenger can open the driver conversation and a driver can select each
accepted passenger, while every other student gets a generic unavailable state.

### 4. Realtime delivery without leaking adjacent conversations

- [ ] Create one client subscription for `messages` inserts filtered by `ride_id`. Treat Realtime as a
      delivery optimization; the shared RLS policy remains the security boundary.
- [ ] On every event, discard rows that are not between the current two participant IDs. Deduplicate by
      message ID so the Server Action response and Realtime event cannot render twice.
- [ ] Unsubscribe on peer/ride change and component unmount. Display reconnecting/offline state and
      keep a manual retry; never erase the already loaded history when Realtime disconnects.
- [ ] Keep the composer keyboard accessible: labelled textarea, Enter-to-send with an explicit
      Shift+Enter newline rule, disabled/pending state, error announcement, and focus restoration.
- [ ] Keep the latest message visible without forcibly stealing scroll position when the user is
      reading older messages. Add an aria-live announcement for newly received messages.
- [ ] Test event deduplication, wrong-peer event rejection, rapid peer changes, cleanup, failed sends,
      and reconnect behavior with a mocked channel. Exercise two real signed-in browser sessions.

Acceptance check: two authorized users exchange messages without refreshing, no third participant's
message appears, and losing Realtime does not lose history or allow unauthorized access.

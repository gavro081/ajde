# Tier 2: trip sharing, ride Q&A, and completed-trip CO2 counters

## Problem Statement

Students can already find rides, request seats, receive driver approval, and exchange contacts after acceptance. They cannot yet share a limited itinerary with a parent, ask questions in a ride-wide thread, or see an estimate of the emissions saved by their completed shared rides. Drivers also have no completion control, despite the database supporting a completed ride status.

These features must build on the working Tier 1 journey without disrupting Dimi's concurrent discovery and AI-search track or overstating the prototype's privacy and emissions guarantees.

## Solution

Deliver Pero's Tier 2 track in three integration checkpoints: passenger-owned expiring trip links and their public itinerary page; authenticated ride Q&A; then driver completion and personal/platform CO2 counters. Each feature is developed on its own branch and integrated serially after verification.

An accepted passenger can create, copy, reuse, and revoke a link that a parent can open without an account. Students viewing an authenticated ride can ask and answer questions and delete their own comments. Drivers can mark departed rides completed, which closes booking decisions and makes eligible accepted passenger seats count toward clearly explained emissions estimates. Both counters appear together on the passenger dashboard.

## User Stories

1. As an accepted passenger, I want to create a share link for my booking, so that a parent can see my itinerary.
2. As an accepted passenger, I want to reuse an active link, so that I can resend the same itinerary without creating unnecessary links.
3. As an accepted passenger, I want to copy my link and see clipboard failures, so that I know whether I can paste it into a message.
4. As an accepted passenger, I want to revoke my selected link, so that subsequent visits no longer reveal my itinerary.
5. As a passenger, I want share controls to show pending, expired, and error states, so that I understand whether sharing succeeded.
6. As a passenger, I want sharing restricted to my own accepted bookings, so that another student cannot create or manage links for me.
7. As a passenger, I want links to expire 24 hours after departure, so that access is bounded without requiring manual cleanup.
8. As a passenger, I want creation refused for cancelled rides or already elapsed expiry times, so that the app does not issue unusable links.
9. As a parent with a link, I want to open the shared itinerary without signing in, so that I can read it without a student account.
10. As a parent with a link, I want to see the route, pickup, departure, driver name/photo, and car make/model/color, so that I understand the planned journey.
11. As a parent with a link, I want loading and unavailable states, so that I understand why an itinerary is not displayed.
12. As a parent with a link, I want the page to explain that it is an itinerary, so that I do not mistake it for live tracking.
13. As a passenger, I want revoked, expired, or cancelled participation to invalidate subsequent public reads immediately, so that old links do not retain access through caching.
14. As a ride participant, I want the public itinerary to omit contacts, other passengers, private messages, and management controls, so that sharing does not disclose unrelated information.
15. As a passenger, I want my token excluded from indexing, referrers, and application analytics/logging, so that using the link does not unnecessarily spread access.
16. As a student viewing a ride, I want to read its Q&A thread, so that I can learn from questions already answered.
17. As a student with a complete profile, I want to post a question on a future published or full ride, so that I can clarify details before travelling.
18. As a driver, I want to answer questions in my ride's thread, so that all eligible viewers can read the answer.
19. As a ride viewer, I want each comment to show its author's name/photo, timestamp, and text, so that the conversation has context.
20. As a commenter, I want a clear warning that other students viewing the ride can read my text, so that I can choose what to disclose.
21. As a commenter, I want whitespace trimmed and empty or oversized comments rejected, so that the thread stays readable.
22. As a ride viewer, I want submitted markup displayed as text, so that reading comments does not execute another user's content.
23. As a commenter, I want to delete my own comment, so that I can withdraw it.
24. As a commenter, I want other users prevented from deleting my comments, so that authorship controls are enforced.
25. As a ride viewer, I want empty states, refreshed content after writes, and submission errors, so that I understand the thread's current state.
26. As a driver, I want comments on private or closed rides rejected by server checks, so that forged requests cannot bypass the page's visibility rules.
27. As a driver, I want to mark my own departed published or full ride completed, so that its lifecycle reflects that the trip has finished.
28. As a driver, I want repeated completion to be safe, so that retrying does not corrupt ride or booking state.
29. As a ride participant, I want completion to preserve accepted bookings and seat counts, so that recording completion does not rewrite participation.
30. As a driver, I want booking decision controls hidden for completed rides and stale approvals rejected on the server, so that new approvals cannot be added after completion.
31. As a passenger, I want my estimated CO2 savings to include only accepted seats on eligible completed rides, so that future or cancelled participation does not inflate my total.
32. As a passenger with multiple accepted seats, I want each seat represented in my estimate, so that the total follows the stated replaced-car assumption.
33. As a student, I want a platform estimate that counts each eligible ride once using its accepted passenger seats, so that joining bookings does not duplicate savings.
34. As a driver, I want the attribution explained, so that I understand why driving does not also credit the same savings to my personal passenger total.
35. As a student, I want counters labelled as estimates with their solo-car baseline, so that I do not mistake them for measured emissions.
36. As a student, I want missing or invalid inputs and unsupported fuels excluded with coverage counts, so that incomplete data is visible rather than silently invented.
37. As a student, I want an understandable empty-history state, so that a lack of eligible completed rides is not confused with a loading failure.
38. As a student, I want platform totals to include records beyond the database's default response limit, so that totals do not silently stop growing.
39. As a passenger, I want cancellation and completion reflected in dashboard totals, so that displayed savings match currently stored participation.
40. As a participant, I want the counter UI to receive aggregates only, so that other passengers' private participation data stays on the server.
41. As a mobile student, I want sharing, Q&A, completion, and impact controls to work on a narrow screen, so that I can use them during travel.
42. As a maintainer, I want Tier 1 booking and contact-visibility regression checks, so that these additions preserve the existing journey.
43. As a project evaluator, I want documentation to distinguish implemented features, assumptions, exclusions, and known authorization limitations, so that I can assess and run the actual prototype.

## Implementation Decisions

- Reuse the existing trip shares, ride comments, rides, bookings, profiles, and car snapshots. The completed ride enum value already exists. No schema change or new AI capability is expected.
- Keep sharing, comments, completion, and impact in separate feature modules with their own validation and server entry points. Reuse existing authentication and request-scoped Supabase helpers without changing their contracts. Every entry point independently checks the authentication, ownership, visibility, and current state relevant to its operation.
- Sharing mutations belong to the authenticated passenger owning the accepted booking. Creation/reuse rejects cancelled rides and elapsed expiry. Revoke deletes the selected owned share record and rechecks ownership and current state. Use the database's unique cryptographically random token default; never derive tokens from booking IDs or expose other users' tokens.
- Set expiry to departure plus 24 hours. Reuse an active share where practical; the existing model does not promise one share per booking. Clearly present expiry, copy failure, loading, and server failures in accepted-booking controls on the passenger dashboard.
- Resolve only the supplied token for the anonymous itinerary. On every read, check that the share exists, is unexpired, still belongs to an accepted booking, and references a non-cancelled ride. Invalid, revoked, expired, or no-longer-accepted shares return an unavailable result. Do not cache access beyond those checks. This requires validity on subsequent reads, not live removal from an already open browser.
- Construct a dedicated allowlisted public projection containing route/pickup, departure, driver name/photo, and car make/model/color. Exclude phone/social contacts, other passengers, private messages, applicant data, and booking controls. Do not expose full database records or a token enumeration endpoint.
- Add no-index metadata and a no-referrer policy. Do not add analytics or application logging that records share tokens. Ensure image requests cannot send the token URL as a referrer. Explain that this is a shared itinerary, not live tracking. Normal ride routes retain their authentication requirements.
- Mount Q&A only on ride detail. Reading follows the current ride-viewing rules: authenticated viewers may see published/full rides; other statuses remain restricted by the existing driver ownership rule. Posting additionally requires a complete student profile, future departure, and published/full status, including for the driver. Recheck these conditions server-side.
- Comments use trimmed text of 1–2000 characters and ordinary text rendering. Display author name/photo, timestamp, empty state, and write errors; explain audience visibility without automatically appending private contact fields. Delete only the authenticated author's own comment and refresh after writes. Driver answers are ordinary comments, not a separate messaging model.
- Add a driver-owned completion action and driver-dashboard control. Check ownership, departed time, and published/full status; an already completed owned ride is an idempotent success. Reject draft, cancelled, future, and non-owned rides. Completion changes only ride status and preserves accepted bookings and seat counts.
- Integrate narrowly with existing dashboard booking decisions: read current ride status and departure, reject decisions outside future published/full rides, and hide decision controls for completed rides. Preserve the existing booking ownership, capacity, state, and cancellation semantics.
- Impact counts only completed, already departed rides with at least one accepted passenger seat. Requested, declined, and cancelled bookings contribute nothing; future, cancelled, and uncompleted rides are ineligible. Use positive finite distance from ride details and consumption from the associated car snapshot; support petrol and diesel only.
- Reuse the pure calculator's exported interface without modifying it or duplicating its fuel factors. Trip emissions equal distance times consumption divided by 100, times the existing factor: 2.31 kg/L petrol or 2.68 kg/L diesel. Ride savings equal trip emissions times accepted passenger seats. Platform totals count each ride once; personal totals attribute the same per-seat value to the passenger holding those seats, with no additional driver credit.
- The calculator also requires positive fuel-price and seat inputs, although trip emissions do not depend on price. Keep that adaptation inside the impact module; a documented positive placeholder price may satisfy the existing interface, with cost outputs discarded. Impact eligibility must not acquire a dependency on fuel-price configuration. This is an implementation clarification derived from the inspected calculator contract.
- Treat missing car data, missing/invalid distance or consumption, and unsupported fuels as exclusions, not zero-emission rides. Return eligible/included/excluded coverage counts with aggregate values and assumptions. Count exclusions per otherwise eligible ride in the relevant personal/platform scope, so multiple bookings do not duplicate excluded-trip counts.
- Keep raw platform participation on the server. Process all eligible rides and bookings with bounded, deterministic pagination that explicitly handles database response limits, including nested booking limits. Return only totals, coverage, and explanatory assumptions to the UI. Distinguish query failures from a successful zero total.
- Mount personal and platform counters together on the passenger dashboard. Revalidate affected totals after completion and cancellation. Explain the separate-car-per-passenger-seat baseline, passenger attribution, supported fuels, exclusions, and that values reflect currently stored trip/car data rather than immutable historical measurements.
- Preserve ownership boundaries: Pero owns the new feature modules/components, passenger and driver dashboard additions, the Q&A mount, and narrow dashboard lifecycle/revalidation integration. Dimi owns discovery, feed/card/filter/view changes, AI/search, dependencies/lockfiles, and environment-example changes. Avoid shared-header, global-style, landing-page, and existing ride-booking-action changes.
- Coordinate any unavoidable database change before implementation. Such a change must include a new migration, updated database-model documentation, regenerated types, and relevant smoke tests together, while preserving Dimi's query compatibility. A reviewed database aggregation function is an alternative only if batching cannot meet requirements.
- Update the root README once after Dimi's checkpoints and final notes are available, reporting actual combined status, setup, sharing/privacy rules, search limitations, and CO2 assumptions. Preserve the known absence of table RLS: server/UI guards do not secure direct database access.

## Testing Decisions

- User-confirmed primary seam: invoke the feature-level server actions and query interfaces consumed by pages, using the existing Vitest runner. Exercise authentication/state checks through those entry points and assert returned data, rejected operations, and persisted effects. Keep any infrastructure doubles at the auth/database/framework boundary; do not assert query-builder call order, component structure, or private helper calls.
- There is no existing browser automation suite or feature action integration harness in the inspected repository. Add only the minimal harness needed for this application boundary; do not invent a separate test seam for each helper. Supplement it with browser verification for behaviors that server-interface tests cannot establish, such as markup escaping, clipboard handling, metadata/referrers, and mobile layouts. Coordinate any new dependency with Dimi.
- Existing prior art includes Vitest input/output tests for ride estimation, booking validation/eligibility, ride views, and location resolution. Reuse their fixture-based arithmetic and boundary-case style. Existing transactional database smoke tests provide rollback-safe prior art for real schema and seat-trigger checks; simulated database responses alone do not establish those guarantees.
- Sharing coverage: accepted owner creation/reuse/revocation; non-owner and anonymous rejection; requested/declined/cancelled booking rejection; cancelled rides; elapsed expiry; malformed, unknown, expired, and revoked tokens; cancellation after sharing; and public payload exclusion of contact, private-message, passenger, and applicant fields. Fix time around the expiry boundary and verify fresh reads after invalidation.
- Q&A coverage: normal student question/driver answer; visibility to another authorized viewer; anonymous/incomplete-profile rejection; private/draft/cancelled/completed/departed posting rejection; whitespace-only and oversized text; 1 and 2000 character boundaries; safe markup display; own-comment deletion; and forged deletion of another author's comment.
- Completion/lifecycle coverage: driver ownership, departed published/full success, future/draft/cancelled rejection, repeated completion, unchanged accepted bookings/seats, and a stale pending approval submitted after completion. Recheck request/approve/decline/cancel and accepted-only contact visibility.
- Impact coverage: petrol/diesel arithmetic; multiple seats and bookings; one contribution per ride; passenger attribution without driver double credit; missing/invalid data and unsupported fuels; empty history; future/uncompleted/cancelled exclusion; accepted booking cancellation; repeat completion; aggregate-only responses; and fixtures exceeding one database page with bookings spanning batch boundaries. Verify both totals and coverage counts, including database-error behavior.
- Concrete arithmetic fixture: a completed 100 km petrol ride consuming 7 L/100 km produces 16.17 kg trip CO2. One passenger with two accepted seats receives 32.34 kg, another with one accepted seat receives 16.17 kg, and the platform receives 48.51 kg once. Cancelling the two-seat booking reduces the platform to 16.17 kg and that passenger's contribution to zero. A 200 km diesel ride at 5 L/100 km produces 26.8 kg per accepted passenger seat.
- Before integration, run the documented test suite, lint, TypeScript check, and Webpack production build. Exercise signed-out shares and invalidation, a two-user question/answer flow, completion ownership, and mobile dashboards. Read the installed framework guides before changing framework code. Report any unavailable live verification honestly rather than claiming it passed.

## Out of Scope

- Rebuilding completed Tier 1 authentication, onboarding, profile, ride creation/import, booking, contact reveal, seat availability, same-gender enforcement, catalog, calculator, or demo-seed functionality.
- Dimi's discovery, natural-language search, match explanations, feed preferences, and associated UI or AI changes.
- Live tracking, live location, public booking/token enumeration, anonymous access to ordinary ride pages, or public contact/applicant disclosure.
- Private chat, realtime Q&A subscriptions, comment editing/history, moderation tools, and ratings.
- Automatic completion, changes to booking seat accounting, or driver credit duplicating passenger savings.
- Measured or certified emissions, immutable historical accounting, invented data defaults, and additional fuel factors.
- A project-wide RLS rollout, new AI credentials, or uncoordinated schema/dependency/environment changes.
- Publishing code or pushing branches without the user's explicit review and push authorization.

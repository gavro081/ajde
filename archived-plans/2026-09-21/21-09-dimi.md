## Phase 1 — deterministic discovery, no OpenAI calls required

### 1. Search contract and feed query (~40 min)

- [ ] Extend `lib/rides/ride-filters.ts` with validated optional departure bounds and an explicit
      `sameGenderOnly` boolean, while preserving existing origin/destination/date/seat URLs.
- [ ] Define the structured search result in `lib/ai/search-query-schema.ts`: canonical location
      IDs, nullable departure bounds, nullable requested seats, confidence, and review warnings.
      Unknown fields remain null. Model output must never become SQL or an unchecked query.
- [ ] Use an explicit current timestamp and `Europe/Skopje` for relative dates. Convert local-day
      boundaries to UTC with daylight-saving handling; do not assume a permanent `+02:00` offset.
- [ ] Define precedence: submitting a new natural-language query replaces previous route/time/seat
      filters with the reviewed result; later manual edits take precedence. Preserve the separately
      chosen same-gender toggle. Clearing search clears its query, interpretation, and explanations.
- [ ] Extend `lib/rides/ride-view.ts` to apply validated bounds and exclude departed rides even when
      a supplied date is in the past. Keep eligibility filtering before the result limit.
- [ ] Add fixed-clock tests for Friday/after-16:00, date-only input, invalid ranges, unknown places,
      manual overrides, existing URLs, and local-day boundaries around daylight-saving changes.

Acceptance check: injected structured filters produce the expected feed without calling OpenAI,
and existing manual filtering still works.

### 2. Same-gender feed preference (~35 min)

- [ ] Add an optional, off-by-default toggle to `/rides`: show drivers of the signed-in passenger's
      same declared gender. Derive the passenger identity and gender on the server.
- [ ] Include both `any` and `same_as_driver` rides when the driver's gender matches. The toggle
      is a passenger filter; it does not change the driver's existing request restriction.
- [ ] Define a usable gender as a declared value other than null or `prefer_not_to_say`. If the
      passenger has no usable value, explain why the toggle cannot be applied instead of guessing.
- [ ] Filter before pagination/limiting. Keep gender lookups server-side and out of ride-card
      payloads, public labels, search responses, and AI prompts.
- [ ] Test toggle-off behavior, matching/nonmatching drivers, missing/undisclosed gender, and that
      the current booking-action restriction still applies independently of the toggle.

Acceptance check: the passenger can narrow discovery without exposing anyone's gender or weakening
the server-side booking rule.

## Phase 2 — structured AI search and explanations

### 3. Natural-language search (~60 min)

- [ ] Implement server-only `parseSearchQuery` in `lib/ai/parse-search-query.ts` using structured
      output and the shared canonical location vocabulary. Reuse the existing resolver through its
      exported interface; do not rewrite post-import or location-resolution code.
- [ ] Add authenticated `POST /api/search` with profile/domain checks, bounded input, schema
      validation, and useful missing-key, refusal, timeout, and invalid-output responses.
- [ ] Resolve raw place wording against canonical candidates and reject fabricated IDs. Interpret
      phrases such as "Bitola Friday after 4" without inventing an origin or passenger preference.
- [ ] Build the search input and interpretation/review UI under `components/discovery/`, mounted
      only by Dimi in `app/rides/page.tsx`. Show readable place names and times, warnings, and a way
      to correct uncertain values using the existing manual controls.
- [ ] Keep manual search usable when the provider fails. Never substitute the development stub for
      a successful production AI result. Preserve filters in the URL for reload/back navigation.
- [ ] Add `fixtures/search/` with Macedonian Cyrillic/Latin, Albanian, landmarks, missing fields,
      relative dates, and unsupported requests. Keep unit tests mocked; run a separate live
      evaluation with a fixed clock and record actual results and known failures.

Acceptance check: a student can enter a query, understand/correct its interpretation, and find
matching rides; malformed or unavailable model output does not break manual discovery.

### 4. Batched match explanations (~45 min)

- [ ] Implement server-only `explainMatch` in `lib/ai/explain-match.ts` and authenticated
      `POST /api/explain`. Accept a bounded list of ride IDs and validated search context; reload
      eligible ride facts on the server instead of trusting client-supplied descriptions.
- [ ] Make one bounded batch call for visible results, not one call per card. Require structured
      `{ rideId, explanation }` results and validate returned IDs, uniqueness, and text length.
- [ ] Send only route, departure, seats, price, and the search criteria needed to explain a match.
      Exclude profiles, contacts, gender, applicant lists, and free-form driver notes.
- [ ] Restrict explanations to supplied matching facts. Do not invent safety, trustworthiness,
      availability guarantees, or preferences. Discard unsupported explanations and use a short
      factual template from validated match facts when necessary.
- [ ] Render optional explanation lines on cards through `components/discovery/`. Keep the feed
      available while explanations load or fail, and ignore stale responses after filters change.
- [ ] Test mismatched IDs, empty results, invented facts, provider failure, and rapid query changes.

Acceptance check: matching cards have concise explanations tied to real search criteria, with no
extra personal data sent to the model and no dependency on explanations for rendering the feed.

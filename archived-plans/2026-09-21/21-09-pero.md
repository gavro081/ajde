## Phase 1 — sharing and communication

### 1. Share-my-trip link creation (~40 min)

- [ ] Add feature-specific actions and validation under `lib/trip-sharing/`. Only the authenticated
      passenger who owns an accepted booking may create, reuse, or revoke its share link.
- [ ] Use the existing `trip_shares` table and its cryptographically random token default. Never
      derive a public token from the booking ID or expose a list of other users' tokens.
- [ ] Set a documented bounded expiry, initially departure plus 24 hours. Refuse creation when
      that expiry is already past or the ride is cancelled. Reuse an active link where practical;
      revocation deletes the selected owned share record.
- [ ] Mount create/copy/revoke controls on accepted bookings in `app/dashboard/trips/page.tsx`.
      Handle pending, clipboard failure, expired links, and server errors clearly.
- [ ] Recheck ownership and current booking/ride state inside every mutation. Keep these actions
      separate from `app/dashboard/actions.ts` so existing booking decisions/cancellation stay stable.

Acceptance check: a confirmed passenger can obtain and revoke a link, while another passenger,
an anonymous visitor, and a pending/declined/cancelled booking cannot create one for that booking.

### 2. Public trip page (~35 min)

- [ ] Build `/trip/[token]` with loading and unavailable states. The recipient can open it without
      signing in. Resolve only the supplied token; do not add public booking/token enumeration.
- [ ] Check expiry, booking acceptance, and ride cancellation on every read. A cancelled booking,
      revoked link, expired token, or cancelled ride must make the page unavailable immediately;
      avoid caching that would retain access after these state changes.
- [ ] Show a minimal projection: route/pickup, departure, driver name/photo, and car make/model/color.
      Explain that it is a shared itinerary, not live tracking. Do not expose phone/social links,
      other passengers, private messages, or booking-management controls.
- [ ] Add no-index metadata and a no-referrer policy for this page. Avoid analytics/token logging
      and loading third-party images in a way that leaks the token URL.
- [ ] Test owner/non-owner creation, invalid/expired/revoked tokens, cancellation after sharing,
      and the public payload's absence of contact and applicant fields.

Acceptance check: a parent can read the shared itinerary in a signed-out browser, and revoked or
no-longer-valid shares stop working without changing the normal authenticated ride routes.

### 3. Public Q&A on a ride (~45 min)

- [ ] Implement comment queries, validation, and actions in `lib/ride-comments/`, reusing
      `ride_comments`. Bound and trim text using the existing 1–2000 character constraint.
- [ ] Build `components/ride-comments/**` and mount the thread only in `app/rides/[id]/page.tsx`.
      Show author name/photo, timestamp, text, empty state, and submission errors.
- [ ] Treat "public Q&A" as visible to everyone allowed to view that ride, unlike private chat.
      Preserve the existing authenticated ride-page boundary; do not make the ride page anonymous.
- [ ] Require a complete authenticated student profile for posting. Recheck ride visibility in
      actions; permit new comments only on future `published`/`full` rides. Do not allow another
      user's draft or cancelled ride to receive comments through a forged request.
- [ ] Render text as text, never raw HTML. Do not automatically include private contact data.
      Tell authors that their questions are visible to other students viewing the ride.
- [ ] Support deleting one's own comment with a server-side ownership check. Refresh the thread
      after writes; realtime subscriptions, edit history, and moderation tooling are outside scope.
- [ ] Test empty/oversized text, unsafe markup rendering, unauthorized post/delete, private rides,
      and the normal question/driver-answer flow without changing booking actions.

Acceptance check: a student asks a question and the driver answers in the ride thread; other ride
viewers can read it, and nobody can delete another author's comment.

## Phase 2 — completed-trip CO2 accounting

### 4. Completion and counter rules (~40 min)

- [ ] Add a small driver-owned "Mark completed" action under `lib/ride-completion/` and mount it in
      `app/dashboard/driver/page.tsx`. The current app has the enum but no completion control.
- [ ] Recheck ownership, departure in the past, and status `published`/`full` on the server. Make
      repeated completion safe and reject draft/cancelled rides. This action changes only status;
      it must not alter accepted bookings or seat counts.
- [ ] Keep pending requests from being accepted after completion: hide decision controls for
      completed rides and add a server-side current-status/departure check to `decideBooking` in
      `app/dashboard/actions.ts`. This file is Pero-owned for this narrow lifecycle integration.
- [ ] Define counters as **estimated CO2 saved on completed shared rides**, not measured emissions.
      Exclude future, cancelled, and uncompleted rides, plus requested/declined/cancelled bookings.
- [ ] Reuse the current petrol/diesel factors and pure calculator through its exported interface.
      For each eligible ride calculate trip emissions from distance and consumption, then multiply
      by accepted passenger seats, assuming each seat replaced a separate car on the same route.
- [ ] Platform total sums each ride once. Personal total attributes the same per-seat estimate to
      the passenger for their accepted seats; do not also add it to the driver's personal total.
      Explain this attribution and the solo-car baseline beside the counters.
- [ ] Skip missing/invalid distance or consumption and unsupported fuels rather than inventing
      values. Report excluded-trip counts. Label results as estimates based on currently stored
      trip/car data, not immutable historical measurements.

Acceptance check: only a driver can complete their departed ride, completed rides cannot receive
new approvals, and everyone uses one explicit, testable rule for counting saved emissions.

### 5. Personal and platform counters (~40 min)

- [ ] Put aggregation/query logic and tests in `lib/impact/`; do not edit Dimi's `ride-view.ts` or
      the existing pure `lib/rides/ride-estimate.ts` calculator.
- [ ] Build `components/impact/**` and mount personal and platform counters together on
      `app/dashboard/trips/page.tsx`. This placement avoids touching the feed, card, header, or
      landing page while still exposing both required counters.
- [ ] Keep raw participation data on the server. Return aggregate values, coverage counts, and
      assumptions to the UI, never a platform-wide list of passengers or private trip details.
- [ ] Handle database result limits explicitly so platform totals do not silently stop at the
      default row limit. Aggregate in bounded batches or use a reviewed database function if needed.
- [ ] Revalidate affected dashboard totals on completion and booking cancellation. Add the small
      required hooks in Pero-owned `app/dashboard/actions.ts`; preserve existing booking semantics.
- [ ] Test petrol/diesel arithmetic, multiple accepted seats/bookings, no double counting, empty
      history, missing data, unsupported fuels, cancellations, and repeated completion.

Acceptance check: a completed fixture ride contributes the expected amount to the platform and
its passengers, while future demo rides and cancelled participation contribute nothing.

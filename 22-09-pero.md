## Product rules locked for this track

- Ratings are post-ride only: the ride must be `completed` and the rater must be a real participant.
- An accepted passenger may rate that ride's driver. The driver may rate each accepted passenger.
- Passengers cannot rate each other. Requested, declined, or cancelled bookings confer no eligibility.
- Each `(ride, rater, ratee)` pair may submit once. No editing or deleting during this deadline.
- Score is an integer from 1 to 5. The optional private note is trimmed and at most 1000 characters.
- Public profile output is aggregate only: average score and count. It must not expose the rater,
  ride, booking, or private note. The rater and ratee may see their own submitted/received detail.
- Render notes as text. AI spam/safety screening, appeals, rating edits, and moderation UI remain
  deferred Tier 3 and must be documented rather than implied.

## Phase 1 — rating eligibility and mutations (~60 min)

### 2. Pure eligibility contract

- [ ] Create `lib/ratings/` with Zod input schemas and a pure eligibility helper. Inputs are server
      facts: current user, ride driver/status, accepted bookings, target user, and any existing rating.
- [ ] Passenger-to-driver eligibility requires the current user's accepted booking on the completed
      ride and `ratee_id = rides.driver_id`.
- [ ] Driver-to-passenger eligibility requires the current user to own the completed ride and the
      target to hold an accepted booking. Reject passenger-to-passenger, unrelated users, self-rating,
      missing/unclaimed drivers, and every non-completed status.
- [ ] Treat the database unique tuple as the final race-condition guard, but return a clear already-
      rated result during normal validation. Map a unique violation to the same harmless result.
- [ ] Test every role/status combination, score bounds, trimmed empty notes, 1000-character boundary,
      repeated submission, multiple accepted seats, and forged ride/ratee IDs.

Acceptance check: only the driver and accepted passengers of a completed ride can rate their actual
counterpart, exactly once.

### 3. Server actions and aggregate queries

- [ ] Add a rating submission action under `lib/ratings/`. Derive `rater_id` from the authenticated
      session, reload the ride/bookings, call the pure eligibility helper, and insert only validated
      values. Never trust role, completion, participant identity, or existing-rating state from forms.
- [ ] Add batched queries for dashboard eligibility/existing ratings; avoid one query per participant.
- [ ] Add a profile summary query using the narrow aggregate function/mechanism from Phase 0. Define
      the no-ratings result as `count: 0` and no misleading five-star default.
- [ ] Revalidate the two dashboards and the ratee's profile after successful submission. Do not alter
      ride status, bookings, seat counts, completion, impact totals, or chat authorization.
- [ ] Keep raw participation and private notes server-side. Test database failures and confirm that a
      failed insert does not display an optimistic success.

Acceptance check: refreshing after submission shows one persistent rating and the correct aggregate,
without changing any ride or booking lifecycle data.

## Phase 2 — post-ride forms and reputation display (~55 min)

### 4. Passenger and driver rating controls

- [ ] Add `components/ratings/**` with accessible 1–5 selection, optional note, pending/success/error
      states, and a submitted read-only state. Use real labels; do not rely only on star icons/color.
- [ ] Mount passenger-to-driver controls on completed accepted bookings in
      `app/dashboard/trips/page.tsx`.
- [ ] Mount driver-to-passenger controls beside each accepted passenger on completed rides in
      `app/dashboard/driver/page.tsx`.
- [ ] Do not render controls for future/published/full/cancelled rides, pending/declined/cancelled
      bookings, demo rows without a real driver, or already rated pairs.
- [ ] Keep forms usable on mobile and by keyboard. Render notes as escaped text and explain that
      aggregate scores affect the profile while written feedback remains private.

Acceptance check: after a completed shared ride, passenger and driver each see only their valid
counterpart controls and cannot manufacture additional targets in the browser.

### 5. Public aggregate and private detail

- [ ] Mount a compact aggregate on `app/profile/[id]/page.tsx`: average to one decimal, total count,
      and an honest empty state. Label it as completed-ride feedback.
- [ ] Never list raw rating rows, rater identities, ride IDs, booking participation, or private notes
      on another student's profile.
- [ ] On the signed-in user's own dashboard, it is acceptable to show their submitted score and note;
      received private-note presentation is optional and must not create additional shared-file scope.
- [ ] Ensure one rating contributes exactly once and aggregate behavior is deterministic under
      concurrent submissions. Add query tests for empty, one, many, and invalid/ineligible rows.

Acceptance check: profiles communicate reputation without revealing who travelled together or the
private feedback attached to a particular ride.

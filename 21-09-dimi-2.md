# Tuesday track A — Tier 3 private ride rooms

This track belongs to **Dimi** and owns one authenticated group-chat room per ride. The room contains
the driver and every accepted passenger; it is not a set of driver/passenger direct messages. Pero
owns the shared database-policy checkpoint and post-ride ratings in
[`21-09-pero-2.md`](21-09-pero-2.md). Chat work starts after Pero's short shared checkpoint is merged
so both tracks use the same reviewed RLS and Realtime foundation.

## Prerequisites — do not start from partial Tier 2

- Merge the completed 21-09 Dimi discovery stack and Pero lifecycle/sharing stack into `main`.
- Merge Pero's `feat/communication-reputation-policies` checkpoint before creating Dimi's first
  chat branch.
- Read `PLAN.md`, `CONTRIBUTING.md`, `ride-share-app/AGENTS.md`, and
  `ride-share-app/supabase/DATABASE_MODELS.md`. Read the installed Next.js guides for Server/Client
  Components, Server Actions, and dynamic routes before changing framework code.
- Reuse the existing `messages` table after Pero adapts it for ride rooms. Do not add a rooms or
  room-members table: the ride is the room and membership is derived from its driver/bookings.

The existing project-wide absence of RLS remains a known limitation, but the new `messages` surface
must have real policies before it is exposed through Realtime. UI checks and Server Actions are not
a substitute for database authorization.

## Product rules locked for this track

- Every ride has at most one private room, identified by `ride_id`.
- Room members are the ride's driver and all passengers whose booking is currently `accepted`.
- Every room message is visible to all authorized members, not only the driver and one passenger.
- Pending, declined, cancelled, and unrelated users cannot read the room or send messages.
- A newly accepted passenger sees messages created from their booking's `decided_at` time onward;
  they do not receive room history from before they joined.
- Cancelling a booking removes that passenger's room access immediately. Cancelling a ride closes
  new sends; remaining authorized participants may retain read-only history.
- New messages require a non-cancelled ride and a departure no more than 48 hours in the past.
- The participant list shows names/photos only. Do not copy phone or social fields into messages.
- Render every body as text. No HTML, Markdown rendering, attachments, links with previews, typing
  indicators, presence, edits, deletes, reactions, private DMs, or read receipts in this deadline.
- Chat is not sent to OpenAI. AI spam/safety screening and moderation tools remain deferred Tier 3.

## Phase 1 — authorization and room message contract (~55 min)

### 1. Server-owned room membership

- [ ] Create `lib/chat/` with pure membership/send-eligibility helpers and server query/action modules.
      Given the signed-in user, ride, and bookings, return a validated room membership or a typed
      denial reason.
- [ ] Recheck `driver_id`, ride status, departure window, and an `accepted` booking on every history
      read and send. Never trust a ride ID, role, sender identity, or participant list from the browser.
- [ ] Derive the room roster server-side as the driver plus deduplicated currently accepted passengers.
      Reject unclaimed rides without a driver and never include requested/declined/cancelled bookings.
- [ ] Keep authorization consistent with Pero's RLS helper/policies. Add unit cases for driver,
      two accepted passengers, pending/declined/cancelled passenger, unrelated student, cancelled ride,
      completed ride inside the send window, and expired send window.

Acceptance check: the driver and every accepted passenger resolve to the same ride room, while URL or
request-payload changes cannot add another user to it.

### 2. Validated room history and send operations

- [ ] Validate UUIDs and trim bodies with Zod. Accept 1–2000 characters at the application boundary,
      even though the existing table permits up to 4000. Return useful empty/oversized errors.
- [ ] Load an initial newest-first page of at most 50 messages, then present it chronologically. Use a
      stable `(created_at, id)` cursor for older pages; never silently rely on Supabase's row limit.
- [ ] Filter history by `ride_id`. The RLS/query layer must enforce the passenger's acceptance time so
      a later participant cannot page into messages created before they joined.
- [ ] Insert with `sender_id` fixed to the authenticated user and room-style `recipient_id = null`.
      Return the inserted row so the UI can reconcile optimistic state. Do not fan one message out into
      duplicate per-recipient rows.
- [ ] Do not implement client-controlled updates or deletes. Treat stored chat as a ride safety record.
- [ ] Test whitespace, maximum length, pagination boundaries, pre-acceptance history exclusion,
      forged sender or non-null recipient, duplicate optimistic reconciliation, database failure,
      and chronological ordering.

Acceptance check: all current members receive the same single stored message, a new member sees only
post-acceptance messages, and every sender identity is server-derived.

      keep a manual retry; never erase the already loaded history when Realtime disconnects.
- [ ] Keep the composer keyboard accessible: labelled textarea, Enter-to-send with an explicit

- [ ] Keep the latest message visible without forcibly stealing scroll position when the user is

- [ ] Test delivery/deduplication with driver plus at least two passenger clients, wrong-ride event

# Sunday track A — identity, profiles, and location resolution

This track owns the user/profile flow and location normalization. It can start immediately; only
the last phase needs the OpenAI API key.

## Already done — do not repeat

- Next.js scaffold and dependencies
- Supabase browser/server clients, environment handling, and session-refresh proxy
- Database schema, triggers, seed cities/pickup points/car models, generated TypeScript types
- `supabase/DATABASE_MODELS.md`

Read `ride-share-app/AGENTS.md` and `ride-share-app/supabase/DATABASE_MODELS.md` before coding.
Do not change the database schema unless a genuine blocker is found. A schema change also requires
the documentation, generated types, and schema smoke test to be updated.

## Phase 1 — no OpenAI key required

Work through this entire phase while the key is unavailable.

### 1. Authentication and access rules (~40 min)

- [ ] Build `/login` with Supabase magic-link sign-in.
- [ ] Add a configurable student-email domain allowlist. Keep the allowed domains in one server-side
      module/environment setting; do not scatter checks through UI components.
- [ ] Add the auth callback/confirmation route required by the installed Supabase SSR version.
- [ ] After sign-in, send users without a complete profile to `/onboarding`; completed users go to
      `/rides`.
- [ ] Show clear states for invalid domain, link sent, expired/invalid link, and sign-out.
- [ ] Protect authenticated pages on the server. Do not rely only on a client redirect.

Acceptance check: an allowed address can request a link, a disallowed address is rejected, and the
redirect behavior is correct for users with and without a profile.

### 2. Onboarding and photo upload (~45 min)

- [ ] Build `/onboarding` for required `full_name`, `photo_url`, and `university`; include the
      optional profile fields only if they do not slow the required flow.
- [ ] Create/configure the profile-photo Storage bucket and its policies, then upload a photo under
      a path owned by the signed-in user.
- [ ] Validate file type/size and show upload/save errors.
- [ ] Upsert the row in `profiles`, then redirect to `/rides`.

Acceptance check: a new authenticated user cannot finish with any required field missing, can
upload and display a photo, and cannot overwrite another user's photo.

### 3. Profile page (~20 min)

- [ ] Build `/profile/[id]` with photo, real name, university, bio, and gender when present.
- [ ] Do not expose phone or social links on the public profile. The plan reserves those for a
      driver and accepted passengers; that authorization belongs in the later RLS/booking work.
- [ ] Add sensible loading, missing-profile, and error states.

Acceptance check: public identity fields render for a real seeded/test profile and contact fields
are absent from the public response and UI.

### 4. Deterministic location resolver (~40 min)

- [ ] Own `lib/ai/resolve-location.ts` and its tests. Despite its directory, this first pass is
      ordinary deterministic code and needs no OpenAI connection.
- [ ] Load canonical cities and pickup points from Supabase (or accept them as injected data so the
      matcher is easy to unit-test).
- [ ] Normalize casing, whitespace, Cyrillic/Latin spelling variants, and diacritics; match against
      `name_mk`, `name_en`, and `aliases`.
- [ ] Return a small stable result contract: entity kind, canonical ID, display name, confidence,
      and `resolution: "alias" | "model" | "unresolved"`.
- [ ] Cover seeded examples such as `Штип`, `Stip`, `кај Мавровка`, `од Рамстор`, and
      `на Автокоманда`.
- [ ] Leave a clearly typed fallback seam for the model, but do not fake model output.

Acceptance check: known city and landmark variants resolve without a network call, and unknown
input returns `unresolved` rather than guessing.

## Phase 2 — start when the OpenAI key arrives

### 5. Model fallback for unresolved locations (~40 min)

- [ ] Add the server-only OpenAI fallback at the seam from phase 1.
- [ ] Give the model only the canonical candidate vocabulary and require a structured response.
- [ ] Never accept a made-up ID: validate the returned ID against the supplied candidates.
- [ ] Keep exact/alias matching first so known locations remain fast, cheap, and deterministic.
- [ ] Add `OPENAI_API_KEY` to `.env.example` with no secret value and confirm it is never exposed via
      a `NEXT_PUBLIC_` variable or client component.

Acceptance check: a known alias makes zero model calls; a genuine miss may use the model; an invalid
model response safely becomes `unresolved`.

### 6. Location tuning and handoff (~30–45 min)

- [ ] Run the resolver over the real-post fixtures supplied by track B.
- [ ] Add aliases only when they are legitimate reusable vocabulary; do not encode entire fixture
      sentences as aliases.
- [ ] Send track B the resolver's exported type/function name and at least the five verified cases.
- [ ] Run lint, type-check/build, and relevant tests; commit this track separately.

## File ownership / collision avoidance

Track A owns:

- `app/login/**`, the auth callback route, and auth guards
- `app/onboarding/**`
- `app/profile/[id]/**`
- profile/auth helpers and profile-photo Storage setup
- `lib/ai/resolve-location.ts` and its tests

Track A should not edit `app/rides/new/**`, `app/rides/import/**`, `app/api/parse/**`, or
`lib/ai/parse-ride-post.ts`; those belong to track B. If a shared type is required, add it as a
small isolated file and tell the other person before changing it.
